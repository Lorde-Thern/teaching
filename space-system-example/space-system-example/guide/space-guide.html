How the space system works

A guided tour of the code that turns Minecraft into a galaxy: how a solar system is described, how planets move, how an endless galaxy fits in a few kilobytes, how you fly from one world to another, and how the sky is painted. Each lesson builds on the one before.

00The big picture

Before any code, hold this picture in your head. Minecraft has dimensions: the Overworld, the Nether, the End. Each is a separate world. Dawnbreak adds one more, called space, which is mostly empty air. Every planet you can visit is still its own world (a dimension), but in space you see them all, at their real positions, moving along their orbits.

So the space system has to do five jobs. Each job lives in its own part of the code:

PackageWhat it holds
galaxy/The data model and the generator: stars, planets, systems, the galaxy itself.
space/Server rules: leaving and entering planets, gravity, running out of air.
network/The packets that keep the client's galaxy identical to the server's.
client/ and client/render/Flight controls, the HUD, the galaxy map and the sky renderer.
world/The asteroid generator for the space dimension.
The one idea to remember. The galaxy is never stored as a big list of planets. It is computed from a seed number whenever someone asks. That single decision explains most of the code you are about to read.

01One dimension called space

data/dawnbreak/dimension/space.json · worldgen/biome/deep_space.json · space/ModDimensions.java

A Minecraft dimension is defined in JSON: what kind of world it is and how to generate its terrain. Space uses the simplest generator there is, a "flat" world, with one layer of air. So the world is empty, and every block of it is the deep_space biome, whose only job is to place asteroids.

{
  "type": "dawnbreak:space",
  "generator": {
    "type": "minecraft:flat",
    "settings": {
      "biome": "dawnbreak:deep_space",
      "layers": [ { "block": "minecraft:air", "height": 1 } ],
      "features": true
    }
  }
}

Java code needs a way to refer to these dimensions. That is what ModDimensions is: a list of keys, like name tags, one per dimension.

public static final ResourceKey<Level> SPACE  = key("space");
public static final ResourceKey<Level> VEGETA = key("vegeta");
// Shared worlds for planets without their own dimension (lesson 06).
public static final List<String> ARCHETYPES = List.of("verdant", "oceanic", "arid", …);

Coordinates in space are ordinary block coordinates, so a star system "at x = 20480, z = 12288" really is twenty thousand blocks from the origin. The galaxy uses Minecraft's own coordinate grid as its map.

02Describing a solar system

galaxy/Orbit.java · Star.java · Body.java · BodyType.java · StarSystem.java · data/dawnbreak/dawnbreak/systems/*.json

Hand-made systems such as Sol or Vegeta are written in JSON. Here is a trimmed version of the Vegeta system:

{
  "position": [20480, 540, 12288],
  "stars": [ { "name": "star.dawnbreak.vegeta_sun", "class": "k", "radius": 240 } ],
  "bodies": [
    {
      "id": "vegeta", "type": "arid", "dimension": "dawnbreak:vegeta",
      "orbit": { "radius": 1500, "phase": 30, "period_minutes": 70 },
      "radius": 150, "atmosphere_radius": 205, "gravity": 2.0
    }
  ]
}

In Java, each piece of that file becomes a record. A record is a small class that just holds values: you list the fields once and Java writes the constructor and getters for you.

public record Orbit(double radius, double phase, double periodTicks, double inclination) { … }
public record Star(String name, …, StarClass starClass, double radius, int color, Orbit orbit) { … }
public record Body(ResourceLocation id, …, BodyType type, Optional<ResourceKey<Level>> dimension,
                   Optional<String> parent, Orbit orbit, double radius, float gravity, …) { … }

Codecs: one object that both reads and writes

How does JSON become a record? Minecraft uses codecs. A codec is a description of a data shape. From that one description, the game can read JSON (or NBT, or network bytes) into objects and write objects back out. Here is the orbit codec:

public static final Codec<Orbit> CODEC = RecordCodecBuilder.create(i -> i.group(
    Codec.doubleRange(0, 1_000_000).fieldOf("radius").forGetter(Orbit::radius),
    Codec.DOUBLE.optionalFieldOf("phase", 0.0).forGetter(o -> Math.toDegrees(o.phase())),
    Codec.doubleRange(0, 1_000_000).optionalFieldOf("period_minutes", 0.0).forGetter(o -> o.periodTicks() / 1200.0),
    …
).apply(i, (radius, phase, period, incl) ->
    new Orbit(radius, Math.toRadians(phase), period * 1200.0, Math.toRadians(incl))));

Read it line by line. Each fieldOf names a JSON key and its type. optionalFieldOf(…, 0.0) means "if it's missing, use 0". The apply lambda builds the record. Notice the unit conversion happening right at the border:

  • JSON is written for humans: degrees, and periods in minutes.
  • Code works in maths units: radians, and time in ticks. Minecraft runs 20 ticks a second, so one minute is 1,200 ticks.

Converting once, at the edge, means no other code ever has to wonder which unit it holds. That's a habit worth copying.

Sensible defaults from the body type

A planet file can leave most things out. Body.codec fills the gaps from the planet's BodyType: an arid world defaults to gravity halfway between its type's minimum and maximum, breathable air if its type has it, and an atmosphere 1.4 times its radius.

atmo.orElse(radius * 1.4),
gravity.orElse((type.minGravity() + type.maxGravity()) / 2F),
breathable.orElse(type.breathable()),

Another detail: "requires_mod". A body can say it only exists when another mod is installed. That's how DMZ's own Namek appears only when Dragon Mine Z is present. StarSystem.codec simply filters those bodies out.

03Making things orbit

galaxy/Orbit.java · StarSystem.java · Galaxy.java

Planets move, but nothing in the code ever moves them. There is no position stored that gets updated every tick. Instead, position is a function of time: give the orbit a time, and it tells you where the planet is.

public Vec3 offset(double time) {
    if (radius <= 0) return Vec3.ZERO;
    double angle = phase + (periodTicks > 0 ? Math.PI * 2 * time / periodTicks : 0);
    double along = radius * Math.sin(angle);
    return new Vec3(radius * Math.cos(angle), along * Math.sin(inclination), along * Math.cos(inclination));
}

Moons orbit planets that orbit stars

A moon names a parent. Its position is its parent's position plus its own orbit offset. The parent might itself have a parent, so the method calls itself. That's recursion:

public Vec3 bodyPosition(Body body, double time) {
    Vec3 centre = body.parent().map(byLocalId::get).map(p -> bodyPosition(p, time)).orElse(position);
    return centre.add(body.orbit().offset(time));
}

Which clock?

Every player must agree where Mars is, so everyone must use the same clock. Galaxy.time uses the level's game time, which every dimension shares with the Overworld, and returns 0 if the server turned orbits off in its config:

public static double time(Level level, float partialTick) {
    return DawnbreakConfig.serverOr(DawnbreakConfig.SERVER.orbitalMotion) ? level.getGameTime() + partialTick : 0;
}

The partialTick is a fraction between ticks. The renderer draws many frames per tick, and adding the fraction makes planets glide smoothly instead of jumping 20 times a second.

04An infinite galaxy from one number

galaxy/Galaxy.java · SystemGenerator.java · StarClass.java · NameGenerator.java

Hand-made systems are few. Everywhere else, systems are generated. The space dimension is cut into square cells, 8,192 blocks on a side, and each cell may hold one system.

Determinism: the same seed always gives the same galaxy

The trick is a seeded random number generator. A random generator started from the same seed produces the same sequence of "random" numbers every time. So if the seed for a cell depends only on the galaxy seed and the cell's coordinates, everyone who generates that cell gets an identical system:

public static Optional<StarSystem> generate(long galaxySeed, int cx, int cz) {
    RandomSource r = RandomSource.create(mix(galaxySeed, cx, cz));
    if (r.nextFloat() > DENSITY) return Optional.empty();   // 40% of cells are empty
    …

mix scrambles three numbers into one. Neighbouring cells (5,7) and (5,8) must get completely unrelated seeds, not nearly equal ones. So it multiplies by large odd constants and folds the bits over themselves with XOR and shifts:

static long mix(long seed, int cx, int cz) {
    long h = seed ^ (cx * 0x9E3779B97F4A7C15L) ^ (cz * 0xC2B2AE3D27D4EB4FL);
    h ^= h >>> 33;  h *= 0xFF51AFD7ED558CCDL;
    h ^= h >>> 33;  h *= 0xC4CEB9FE1A85EC53L;
    return h ^ (h >>> 33);
}

What the generator decides, in order

  1. Position: the middle of the cell, nudged up to 15% of a cell sideways, so systems don't sit on a perfect grid.
  2. Stars: one primary, picked by weighted chance. Red dwarfs (class M, weight 28) are common and blue giants (class O, weight 1) are rare, like the real galaxy. About 14% of systems get a companion star and 4% get two.
  3. Habitable zone: 700 + primaryRadius × 3.2 blocks out. Bigger, brighter stars push it further away.
  4. Planets: 1 to 6, walking outward. Each planet's type depends on its distance from the habitable zone: hot rock close in, earth-like worlds in the zone, gas and ice giants far out.
  5. Orbit periods: 20 × (orbit/1000)^1.5 minutes. That exponent is Kepler's third law: further planets are slower.
  6. Moons: giants get up to two; large rocky planets sometimes one.
  7. Asteroid belt: a 35% chance.
  8. Names: stitched from syllables ("Zarneth", "Kalix") by NameGenerator, using the same random generator, so names are deterministic too.

Generate on demand, remember a little

The galaxy is effectively infinite, so it can't generate everything up front. Galaxy.proceduralAt generates a cell the first time anyone asks and keeps the result in a cache:

private final Map<Long, Optional<StarSystem>> cells = Collections.synchronizedMap(
    new LinkedHashMap<>(256, 0.75F, true) {
        protected boolean removeEldestEntry(Map.Entry<…> eldest) { return size() > CACHE_SIZE; }
    });

public Optional<StarSystem> proceduralAt(int cx, int cz) {
    long key = ((long) cx << 32) | (cz & 0xFFFFFFFFL);
    return cells.computeIfAbsent(key, k -> blockedByHandcrafted(cx, cz) ? Optional.empty() : SystemGenerator.generate(seed, cx, cz));
}

Three tricks in a few lines:

  • A long as a map key. Two 32-bit cell numbers are packed into one 64-bit number, which makes a cheap, unique key.
  • An LRU cache in one class. A LinkedHashMap created with true keeps entries in order of last use. Overriding removeEldestEntry throws out the least recently used cell once there are more than 8,192. That's a complete "least recently used" cache.
  • Caching "nothing here". Empty cells are stored as Optional.empty(), so an empty cell is only ever computed once too.

Procedural systems still need ids so other code can point at them. The id encodes the cell: dawnbreak:proc/12/-4. To find the system for an id, Galaxy.system reads the two numbers back out and regenerates the cell. A planet's id is its system id plus a local name (…/proc/12/-4/b2), which Galaxy.body splits at the last slash.

05Loading and syncing

galaxy/SystemLoader.java · Galaxies.java · network/SyncGalaxyPacket.java

Minecraft runs as two programs: the server, which owns the true state of the world, and the client, which draws it. In singleplayer both run in the same Java process, so there are two galaxies in memory at once. Galaxies keeps one per side:

private static volatile Galaxy server = Galaxy.EMPTY;
private static volatile Galaxy client = Galaxy.EMPTY;

public static Galaxy get(Level level) { return get(level.isClientSide()); }

volatile means the field is always read fresh. The server thread and the render thread can both see the new galaxy the moment it's replaced.

Reading the JSON files

SystemLoader is a reload listener. Minecraft calls it whenever data packs load, at startup or on /reload. It parses every file in dawnbreak/systems/, skips (and logs) broken ones, and rebuilds the server galaxy. It also keeps the raw JSON text, because that's what it will send to clients.

What crosses the network

When a player joins, the server sends one packet: a seed and the raw JSON of the hand-made systems. It does not send planets. The client parses the same JSON and builds its own Galaxy from the same seed:

public void handle(Supplier<NetworkEvent.Context> ctx) {
    List<StarSystem> parsed = new ArrayList<>();
    systems.forEach((id, json) -> SystemLoader.parse(id, json).ifPresent(parsed::add));
    Galaxies.setClient(new Galaxy(seed, parsed));
}

Because generation is deterministic, the client's procedural systems come out identical to the server's without a single planet being sent. A few kilobytes describe the whole galaxy.

A weakness worth knowing. The server doesn't send the world seed itself. It sends mix(worldSeed, 0x6A1A, 0xC7), and a comment says this keeps the world seed private. But every step of mix can be undone: XOR with a known value, multiplying by an odd constant, and "XOR with yourself shifted right" are all reversible. A determined player could recover the world seed from the galaxy seed and use it to find structures. A one-way hash, such as SHA-256 of the seed, would fix this.

06Planets as places

galaxy/Body.java · BodyType.java · GalaxyData.java · Bodies.java · network/CurrentBodyPacket.java

A planet you can land on needs a world to land in. There are two cases:

  • Planets with their own dimension. Vegeta, Elementia and the Moon each have one, named in their JSON with "dimension".
  • Everything else, including thousands of procedural planets. Making a dimension for each would be impossibly expensive. Instead, every planet of a type shares one archetype world: all desert planets land in world_arid, all ocean planets in world_oceanic, and so on.
/** Where you land: the body's own dimension, or its type's shared archetype world. */
public Optional<ResourceKey<Level>> landingDimension() {
    return dimension.isPresent() ? dimension : type.archetypeDimension();
}

Gas giants return empty here, which is how the code says "you can't land on this".

Sharing one world without meeting

If every desert planet lands in the same world, why don't two of them overlap? Each planet is given its own slot: a 20,000-block square region of that world. GalaxyData hands out slots and saves them with the world, so a planet keeps its slot forever:

public long slotFor(Body body) {
    Long existing = slotsByBody.get(key);
    if (existing != null) return existing;
    // Pick a slot from a hash of the planet's id; if it's taken, walk to the next free one.
    …
    while (bodiesBySlot.containsKey(slot) || (sx == 0 && sz == 0)) { … }
    slotsByBody.put(key, slot);
    bodiesBySlot.put(slot, key);
    setDirty();   // tell Minecraft to save this
    return slot;
}

It keeps two maps, planet→slot and slot→planet, so the question can be asked either way. Slot (0, 0) is never handed out, which keeps the area around each archetype world's spawn free. SavedData is Minecraft's built-in way to store a mod's own data inside the world save.

"Which planet am I on?"

Almost every rule needs this answer: gravity, air, travel. Bodies.at answers it:

public static Optional<Body> at(Level level, double x, double z) {
    Optional<Body> fixed = galaxy.bodyForDimension(level.dimension());   // Vegeta? Elementia?
    if (fixed.isPresent()) return fixed;
    if (!ModDimensions.isArchetype(level.dimension())) return Optional.empty();   // the Overworld etc.
    if (level.isClientSide()) return Optional.ofNullable(clientCurrent).flatMap(galaxy::body);
    return GalaxyData.get(server).bodyAt(x, z)…;   // which slot is this position in?
}

The client doesn't have the saved slot table, so the server sends a small CurrentBodyPacket whenever your planet changes. SpaceEvents.syncBody remembers what it last sent each player and only sends again when the answer changes.

07Travel between worlds

space/SpaceTransit.java · SpaceEvents.java

Every tick, for every player, SpaceEvents.onPlayerTick calls SpaceTransit.tick. That checks two situations:

Leaving a planet

Fly high enough (the build limit plus a configurable margin, 64 blocks by default) and breakOrbit runs. It works out where the planet is in space right now and puts you just outside its atmosphere, in the direction you're facing. It also writes down where you left from, in rememberDeparture.

Landing

In space, the code checks your distance to each planet. Inside an atmosphere, enterAtmosphere picks a landing spot in this order:

  1. where you last left this planet (the departure you wrote down), so you come back to your base;
  2. else, for a planet with its own dimension, that world's spawn point;
  3. else, the middle of the planet's slot in its archetype world.

It drops you just above the build limit and gives you slow falling for the descent. The arrival height is deliberately lower than the exit height (min(arrivalOffset, margin − 16)). Otherwise you would arrive above the exit line and be thrown straight back into space.

Three safety habits

  • A cooldown after every trip (TAG_COOLDOWN), so you can't bounce between worlds every tick.
  • Teleports are queued, not done on the spot. schedule puts the trip in a PENDING queue, run at the end of the server tick. Moving a player to another dimension while the game is still looping over that world's players can break the loop. Doing it afterwards is always safe.
  • Cheap checks. Checking every system in the galaxy every tick would be slow. Once a second the code lists the systems close enough to matter (NEARBY), and on the other 19 ticks it checks only those.

Ships use the same rules through tickCraft, with one extra problem. When a vehicle changes dimension, Minecraft throws its passengers off. So moveCraft moves the ship and each passenger separately, then seats everyone again five ticks later (REMOUNTS), once their game has received the ship.

08Gravity, air and flight

space/gravity/GravityHandler.java · space/VacuumHandler.java · SpaceSurvivalEvent.java · client/SpaceFlightControls.java

Gravity through attributes

Minecraft entities have attributes: numbers such as max health or movement speed, which other code adjusts with modifiers. Forge adds one called entity_gravity. To give a planet 2× gravity, the code adds a modifier that multiplies it:

double gravity = multiplier(entity);   // e.g. 2.0 on Vegeta, from Bodies.at(...)
setModifier(entity.getAttribute(ForgeMod.ENTITY_GRAVITY.get()), GRAVITY_ID, "Dawnbreak gravity", gravity - 1.0);

Why gravity − 1.0? The MULTIPLY_TOTAL operation multiplies the value by (1 + amount), so an amount of 1.0 doubles it. The fixed UUID means the code can find and replace its own modifier later instead of stacking a new one each time. Attributes also sync to the client automatically, and that matters: movement is calculated on the player's own computer, so the client must feel the gravity too. Heavy gravity also adds a speed penalty that grows with the logarithm of gravity: −25% at 10×, −50% at 100×.

Running out of air

The air bar is vanilla's underwater air. But vanilla refills it every tick you aren't underwater, so simply lowering it wouldn't work. VacuumHandler keeps its own count in the player's saved data, lowers that, and writes it over vanilla's value at the end of each tick:

int oxygen = data.contains(TAG_OXYGEN) ? data.getInt(TAG_OXYGEN) : player.getAirSupply();
if (player.level().getGameTime() % interval == 0) oxygen--;
if (oxygen <= -20) { oxygen = 0; player.hurt(player.damageSources().drown(), 2.0F); }
player.setAirSupply(oxygen);   // overwrite vanilla's refill

Before draining anything, exposed() asks whether you're actually in danger: creative mode, sitting in a spacecraft, or wearing a Capsule Breather all protect you. Last, it posts an event, SpaceSurvivalEvent. Any other mod can listen and cancel it to say "this player can breathe". That's how DMZ races or other mods' space suits can plug in without Dawnbreak knowing about them. Posting an event like this is called an extension point.

Flying

SpaceFlightControls runs only on the client, because player movement is client-authoritative: your own game moves you and tells the server. Hold Sprint and Forward and a "cruise" speed builds up. Each tick the code tops up your velocity along where you're looking:

double along = velocity.dot(look);   // how fast you're already going that way
if (along < cruise) player.setDeltaMovement(velocity.add(look.scale(cruise - along)));

The dot product measures how much of your current velocity already points where you look. Only the shortfall is added, so turning feels smooth instead of snapping.

09Drawing the sky

client/SpaceSkyEffects.java · client/render/SpaceRenderer.java · FarField.java · Meshes.java · texture/* · assets/dawnbreak/shaders/core/*

Minecraft lets a dimension replace its sky drawing. SpaceSkyEffects.renderSky hands the whole job to SpaceRenderer.render, which draws, back to front:

  1. a nebula backdrop and thousands of faint background stars;
  2. the far field: a dot for every star system within range, plus asteroid belts and orbit lines;
  3. the systems you're in or near, in full: textured, lit, spinning planets with clouds, rings and atmospheres.

The same renderer draws the sky when you stand on a planet. Then the viewpoint is set to that planet's position in space, just above its surface, so the sky shows exactly what you'd see from there, including the other planets.

The big problem: space is too big to draw

A graphics card only draws things between a near and a far limit. Minecraft's far limit is a few hundred blocks, but a neighbouring planet might be 3,000 blocks away and a star 50,000. The fix is clever. Each object is drawn at a fake, compressed distance, and also shrunk by the same factor:

/** Compressed draw distance: monotonic, so depth order survives, and always inside the far plane. */
private static double skyDistance(double dist) {
    return 10 + 8 * Math.log1p(dist / 20);
}
…
double k = skyDistance(dist) / dist;
shader.safeGetUniform("BodyCenter").set(rel.x * k, rel.y * k, rel.z * k);
shader.safeGetUniform("BodyScale").set(radius * k);

Why does this look right? How big something appears depends only on size ÷ distance. Multiply both by the same factor k and the ratio doesn't change. A planet drawn 50 units away and shrunk to match looks exactly as big as the real thing 3,000 blocks away. The player can't tell the difference.

Level of detail

The renderer works out how many pixels each object covers on screen (pixels()), then chooses how much effort to spend:

On-screen sizeWhat gets drawn
under 1.5 pxa glowing dot, brighter on its sunlit side (lit), never smaller than about 1.3 px, so every planet in a system can still be found
1.5 – 20 pxthe low-detail sphere mesh
20 – 110 pxthe medium sphere
over 110 pxthe detailed sphere; textures also switch to higher resolutions at 48 px and 200 px

Drawing order

Instead of drawing as it goes, the renderer collects jobs into three lists: solid bodies, see-through layers (clouds, rings) and atmosphere halos. It sorts each list from farthest to nearest and runs them in that order. This is the painter's algorithm: like painting a landscape, you paint the mountains before the tree in front of them. It matters most for see-through layers, which must be drawn after whatever is behind them.

Shaders spin the planets

The spinning and tilting happens on the graphics card, in planet.vsh. The mesh is a sphere of radius 1, so a point on it is also the direction straight out from the surface. Rotate it, scale it and move it into place:

vec3 p = rotateX(rotateY(Position, Spin), Tilt);   // spin about the axis, then tilt the axis
vec3 world = BodyCenter + p * BodyScale;          // the compressed position and size from above
gl_Position = ProjMat * ModelViewMat * vec4(world, 1.0);

Doing heavy work off the main thread

Two jobs are too slow to do while drawing a frame:

  • The far field. Thousands of star dots, belts and orbit lines. FarField builds them on a worker thread whenever you cross into a new galaxy cell, uploads them to the graphics card once, and reuses them every frame. The distance compression is done per vertex in the shader, against the live camera, so the dots stay accurate while you fly and nothing needs rebuilding.
  • Planet textures. Every planet's surface is painted from noise in code; there are no texture files. SpaceTextures generates them in the background in three resolutions, and the renderer uses a flat colour until they're ready.

10Asteroids

world/AsteroidFeature.java · AsteroidConfiguration.java · worldgen/biome/deep_space.json

Asteroids are the only real blocks in space. They're a feature, Minecraft's name for anything placed during world generation (trees, ores, boulders). The deep_space biome lists three: plain asteroids, ore-rich ones, and belt asteroids.

Placement uses the galaxy model again. A belt asteroid only appears if this spot is within an asteroid belt's ring, and it's then moved to the belt's height. A plain asteroid is mostly skipped inside a system (80% of the time), so orbits stay clear:

if (belt) {
    if (inside a belt ring) return new BlockPos(x, beltHeight ± 45, z);
} else if (dist < system.extent() && random.nextFloat() > 0.2F) {
    return null;   // keep systems mostly clear
}

The rock itself is a squashed sphere: each axis gets its own random radius. Its edge is made lumpy by adding three sine waves at random offsets. Blocks near the surface become the shell; inside, a random roll decides between core stone and ore. The radius is capped at 10 blocks for a practical reason. A feature may only write to the 3×3 chunks around where it starts, and a bigger rock would break that rule.

11Recap and exercises

The design ideas, in one list:

  • Compute, don't store. Positions are functions of time, and procedural systems are functions of a seed.
  • Determinism replaces networking. Same seed, same code, same galaxy on every computer.
  • Convert units at the border. Humans write degrees and minutes; code thinks in radians and ticks.
  • Share expensive things. Archetype worlds give thousands of planets five dimensions, split into saved slots.
  • Be careful about timing. Queue teleports until the tick ends, and re-seat passengers a few ticks later.
  • Spend effort where it's visible. Level of detail, a cached far field and background texture generation.
  • Leave doors open. SpaceSurvivalEvent lets other mods change the rules without editing this code.

Try these

  1. Write a new system JSON with one star and a moon that orbits a moon. Which method makes the second moon work without any new code? (Lesson 03.)
  2. Two players far apart both look at cell (40, −12). Explain, step by step, why they see the same system. What would break if SystemGenerator called Math.random() instead of r.nextFloat()?
  3. Set arrivalHeightOffset higher than orbitExitMargin in your head. What happens to a player who enters an atmosphere? Find the line in enterAtmosphere that prevents it.
  4. Using skyDistance, work out how far away a star 10,000 blocks off is drawn, and what factor its radius is multiplied by. (Answer: about 59.7 units, so it's scaled by about 0.006.)
  5. Fix the weakness from lesson 05: make the galaxy seed impossible to turn back into the world seed, without changing how procedural systems are generated from it.
